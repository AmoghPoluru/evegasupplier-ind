# evegasupplier-ind: Admin Console design (matching evega's `/staff`)

Design only — no code written yet. Goal: bring `evegasupplier-ind`'s admin area up to the same shape, depth and UX as evega's admin dashboard (`src/app/(app)/staff`).

## 1. Where each repo stands today

### evega (reference)
- Route group `(app)/staff`, guarded by `requireAppAdmin()` (admin + BDO = "app staff"), `AdminSidebar` (dark gray-900 rail) + `AdminHeader` (account dropdown, logout, storefront link), scrollable `<main>` on gray-50.
- 9 sections: Vendors, Digital Marketing, Potential Vendors, Products, Orders, Customers (placeholder), Users, Templates, Happy Banner.
- Consistent page pattern: client page → tRPC list query with `search` (300ms debounce) + status/vendor/date filters + pagination → table with **inline editable rows** (`EditableProductRow`, `EditableOrderRow`) and/or edit dialogs (`StaffVendorEditDialog`, `StaffUserEditDialog`), `sonner` toasts, `Skeleton` loading, `Badge` status chips.
- Backed by one `src/modules/admin/server/procedures.ts` (~1.6k lines) with `staffProcedure` / `adminProcedure` separation; includes admin-only **impersonation** (sign in as any user, return-to-admin banner) and staff **manual order creation**.
- No stats/overview page — `/staff` redirects to a section.

### evegasupplier-ind (current)
- `(app)/app-admin` guarded by `requireAdmin()` (role `admin` only), light `bg-gray-100` sidebar + fixed header, `p-6 ml-64` main.
- Existing: `dashboard` (7 stat cards + pending vendors/buyers cards + recent orders widget), `suppliers` (list, filters, detail modal, edit/delete dialogs), `buyers` (list, approve/reject, edit/delete, detail modal), `products` (list, form, create/edit/delete), `vendors/pending`.
- `src/trpc/routers/admin.ts` (~1.3k lines) with a locally-defined `adminProcedure`; routers: `dashboard.stats`, `vendors.*`, `buyers.*`, `products.*`, `orders.recent`.

### Concrete gaps
1. **Sidebar "Orders" links to `/app-admin/orders`, which does not exist** → 404. `RecentOrdersWidget` also links to `/app-admin/orders/[id]`.
2. No **Users** page (roles `user | vendor | buyer | admin | bdo` are only editable in Payload admin) and no impersonation.
3. No admin views for collections that exist: `Inquiries`, `Quotes`, `RFQs`, `SampleRequests`, `BdoConversations`/`BdoChatMessages` (BDO console exists at `/bdo` but is not reachable/manageable from admin).
4. **Duplicate legacy route** `(app)/admin/vendors/pending` alongside `(app)/app-admin/vendors/pending` — same components, two URLs.
5. `dashboard.stats` does full-collection fetches (`limit: 1000` on vendors and orders, in-memory pending filter and revenue sum) — will degrade and is already approximate; several `as any` casts.
6. No BDO access tier: everything is admin-or-nothing, while evega distinguishes `staffProcedure` from `adminProcedure`.

## 2. Target design

### 2.1 Shell & IA
Keep the URL prefix `/app-admin` (avoids collision with Payload's `/admin`); delete the legacy `(app)/admin/*` group and redirect it to `/app-admin/*`.

Adopt evega's shell for density: full-height flex layout (`h-screen`, sidebar `w-64` dark, header 16, `main` scrolls, `bg-gray-50`) instead of the `fixed` + `ml-64` approach, so long tables scroll inside main and the header/sidebar never overlap.

Sidebar groups (new items in **bold**):

| Group | Items |
|---|---|
| Overview | Dashboard |
| Supply | All Suppliers, Pending Suppliers, Products |
| Demand | All Buyers, **Orders**, **RFQs & Quotes**, **Inquiries**, **Sample Requests** |
| Platform | **Users**, **BDO Console** |

Header: page-context label + avatar dropdown (name/email, My Profile, Log out) + "View marketplace" link in the sidebar footer — same as evega's `AdminHeader`/`AdminSidebar`.

### 2.2 Dashboard (rework of the existing page)
- Row 1 — stat cards, computed with `limit: 0` count queries + one aggregation for revenue (no `limit: 1000` scans): Suppliers (total / pending / approved), Buyers (total / pending), Products (total / published / draft), Orders (total / open), Revenue (30d + all-time), Open RFQs.
- Row 2 — action queues: Pending Suppliers, Pending Buyers, Open RFQs, each a compact card with count + approve/reject inline actions and "View all".
- Row 3 — Recent Orders and Recent Suppliers widgets (already exist; `RecentVendorsWidget` is currently unused — wire it in).
- Keep `Suspense` + `DashboardSkeleton`.

### 2.3 New pages (each follows the evega table pattern)
- **Orders** (`/app-admin/orders`, + `/[id]`): filters = status, supplier, buyer, date range, search; paginated table; `EditableOrderRow` equivalent for status/qty/price edits with a status history trail; "Create manual order" dialog (mirrors evega's staff manual order flow, fits this repo's phone-based manual checkout). Fixes the broken links.
- **Users** (`/app-admin/users`): list all users with role badges, search + role filter, edit dialog (name, email, role, linked vendor/buyer, password reset). Admin-only "Sign in as user" (impersonation) with a return-to-admin banner, ported from evega's `admin.users.impersonate` (Payload JWT + cookie swap, `impersonator` cookie).
- **RFQs & Quotes** (`/app-admin/rfqs`): RFQ list with buyer/supplier/status filters, detail drawer showing quote thread, admin ability to nudge/close.
- **Inquiries** (`/app-admin/inquiries`) and **Sample Requests** (`/app-admin/sample-requests`): read + status-change lists, same table primitives.
- **BDO Console** (`/app-admin/bdo`): BDO roster, conversation volume, link into `/bdo/inbox/[conversationId]`.
- **Pending Suppliers**: keep, moved under the Supply group (existing `PendingVendorsList` reused).

### 2.4 Data layer
- Split `src/trpc/routers/admin.ts` into `src/modules/admin/server/*` per domain (`vendors`, `buyers`, `products`, `orders`, `users`, `rfqs`, `dashboard`) as in evega — the single file is already at 1.3k lines and would roughly double.
- Move `adminProcedure` into `src/trpc/init.ts` and add `staffProcedure` (admin **or** bdo). Read-heavy lists → `staffProcedure`; approvals, deletes, role edits, impersonation → `adminProcedure`.
- Standardize list inputs on one shared Zod schema (`search`, `status`, `page`, `limit`, `sortBy`, `sortOrder`) and one `{ docs, totalDocs, page, totalPages }` response shape.
- Replace `as any` collection/field casts with generated `payload-types` (run `npm run generate:types`).

### 2.5 Visual language
Match evega: dark sidebar (gray-900, emerald accent, active = gray-800), white cards with `border-gray-200`, `Badge` status chips (green active / yellow pending / orange suspended / red rejected), `Skeleton` loaders, `sonner` toasts, `Table` primitives — all of which already exist in `src/components/ui`, so no new dependencies.

## 3. Suggested phasing (my own throughput, not team-weeks)

| Phase | Scope | Est. |
|---|---|---|
| 1 | Shell + sidebar/IA rework, delete legacy `(app)/admin`, dashboard stats rewrite (count queries), wire `RecentVendorsWidget` | ~0.5 session |
| 2 | Orders list + detail + inline edit + manual order dialog (fixes 404s) | ~1 session |
| 3 | Users page + role editing + impersonation | ~0.5–1 session |
| 4 | RFQs/Quotes, Inquiries, Sample Requests, BDO console | ~1 session |
| 5 | Router split into `src/modules/admin/server`, `staffProcedure` tier, type cleanup | ~0.5 session |

Phases 1–2 are the highest value (they remove broken navigation); 5 can be folded into whichever phase touches the router most.

## 4. Open questions
1. Should BDOs get read access to the admin console (evega's `staffProcedure` model), or stay admin-only?
2. Keep `/app-admin` as the prefix, or rename to `/staff` for parity with evega?
3. Impersonation — do you want it here, given the auth stack differs (plain Payload `payload.auth` vs evega's cached session helpers)?
4. Priority order: is Orders first the right call, or do you want RFQs/Quotes (core B2B flow) ahead of it?

## 5. BDO role & assignment — decision 2 (the big one)

You asked to remove the BDO *chat* collections. Separate from that, the BDO **role** is woven into data and access control:
- `Users.role` option `bdo`.
- `Vendors.bdo` + `Vendors.bdoAssignedAt` and `Buyers.bdo` + `Buyers.bdoAssignedAt` — relationship fields with field-level access rules, `beforeChange` validation ("BDO field must reference a user with role Admin or BDO"), and auto-stamping of assignment time. Both collections list `bdo` in `admin.defaultColumns`.
- `src/seed/seed.ts` `ensureSubbuBdoUserAndAssignAll` + `src/seed/seed-subbu-bdo.ts` + the `db:seed:bdo` npm script, which create `subbu.poluru@gmail.com` as `bdo` and assign them to every supplier and buyer.
- `(app)/bdo/*` route group and role gating.

Three options:
- **A. Chat only** — delete the 2 BDO collections + `chat` router + `src/components/bdo` + `(app)/bdo/inbox`, but keep the `bdo` role, the assignment fields, and a BDO dashboard. Smallest change; BDOs keep coordinating without in-app chat.
- **B. Full BDO removal** (my recommendation if BDOs aren't part of the product): also drop the `bdo` role option, the 4 fields + their hooks/access rules on Vendors/Buyers, the `(app)/bdo` group, the BDO seeds and npm script, and the nav/redirect logic. Requires a **data migration** to unset `bdo`/`bdoAssignedAt` on existing docs and reassign any existing `role: 'bdo'` users (→ `user`?).
- **C. Full removal but keep the role as a staff tier** — drop chat + assignment fields, keep `role: 'bdo'` purely as a read-only admin-console tier (ties into open question 1 of the admin design doc).

## 6. Data / migration notes

- Mongo collections `rfqs`, `quotes`, `inquiries`, `sample-requests`, `bdo-conversations`, `bdo-chat-messages`, `messages` become orphaned. Payload/Mongoose won't drop them — I'd add a one-off script (`src/scripts/`) that drops them, run manually, so nothing is destroyed implicitly by a deploy.
- `RFQs.selectedQuote` and `Quotes.rfq` cross-references disappear with both collections, so no dangling relationships remain outside the ones in section 5.
- I'd verify with `npx tsc --noEmit` + `npx eslint` on touched files, plus a `npm run build` (needs `DATABASE_URL` / `PAYLOAD_SECRET`).
